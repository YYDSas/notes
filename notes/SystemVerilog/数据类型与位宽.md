> 本篇聚焦「位宽」这条主线：**维度写在哪、宽多少、赋值时补位还是截断**。
> 这三件事决定了大多数"看着对、结果是错的"的静默 bug。结论均在本机 QuestaSim 10.7c 实测。

## 一、打包 vs 非打包：写在名字哪一边

```systemverilog
bit [3:0][7:0] arry [2:0];
//  ← 左：打包维度（32 bit）   → 右：非打包维度（3 个元素）
```

| 写在 | 名称 | 特点 |
| --- | --- | --- |
| 变量名**左边** | **打包维度** packed | 可整体赋值、可切片、连续存储 |
| 变量名**右边** | **非打包维度** unpacked | 只能逐元素访问、或整体用赋值模式 |

- `arry` = 3 个元素 × 每个 4 字节 → `$bits(arry)=96`、`$size(arry)=3`、`$bits(arry[0][0])=8`
- 索引：`arry[i]` → 32 bit 向量；`arry[i][j]` → 8 bit；`arry[i][j][k]` → 1 bit
- 位序：打包维度**最左 = 最高位**。`arry[0][3]` 是 bit31:24，`arry[0][0]` 是 bit7:0

> 判断补位还是截断，**先问那个索引选出的是"打包切片"还是"非打包元素"**——这一步错了，后面全错。

## 二、$bits / $size / $dimensions 速查

| 调用 | 含义 |
| --- | --- |
| `$bits(x)` | 总位数（含所有维度） |
| `$size(x)` | **第一维**的元素个数 |
| `$size(x, n)` | 第 n 维的元素个数 |
| `$dimensions(x)` | 维度总数（打包 + 非打包） |
| `$unpacked_dimensions(x)` | 非打包维度数 |

**对比表（实测）**：

| 项 | `bit [7:0][3:0] nib` | `bit [31:0] vec` |
| --- | --- | --- |
| `$bits` | 32 | 32 |
| `$dimensions` | 2 | 1 |
| `$size` | `8`（`$size(nib,2)=4`） | `32` |
| `[0]` 的宽度 | **4 位** | **1 位** |
| `x[9][0]` | `nib[i][j]` 合法 | `vec[9][0]` **语法错误** |

- **位模式完全一致**：`nib == vec` 为真，可互相直接赋值。等价关系 `nib[i][j] ≡ vec[4*i + j]`
- 全宽切片 `nib[31:0]` → **出界警告** `vopt-2697 MSB of part-select ... out of bounds`（碰巧生效但不可靠）
- 遍历时 `$size(nib)` 只给 8；想要 32 位要用 `$bits(nib)` 或双层 `nib[i][j]` 循环

**选型**：按字段访问（32 位寄存器拆 8 个 nibble）用 `[7:0][3:0]`；需要任意位选/切片/整体比较用 `[31:0]`。

## 三、位宽不匹配赋值：静默扩展 / 截断

```systemverilog
bit [3:0][7:0] arry [1:0];   // $bits(arry[0]) = 32
arry[0] = 16'hFF;            // 16 位 → 32 位
// 实测：arry[0] = 32'h0000_00FF（高位零扩展）
```

| 情形 | 结果 | 有没有警告 |
| --- | --- | --- |
| 右 16 位 → 左 32 位 | 高位**零扩展** `0000_00FF` | ❌ 无 |
| 右 64 位 → 左 32 位 | 只留低 32 位 | ❌ 无 |

> ⚠️ **两个方向都不报错也不报警告**（实测 `Warnings: 0`），全靠人工检查。
> 想要满字节 FF 要写 `32'hFFFF_FFFF` 或 `{4{8'hFF}}`；`16'hFFFF` 只会得到 `0000ffff`。

**另一个静默点**：`bit` 是 2-state，未赋值的元素是 `0`；`logic` 是 4-state，未赋值是 `x`。

## 四、重复拼接 `{n{expr}}`

- 规则：内层复制 n 份首尾相接；**位宽 = 内层位宽 × n**（自决定，不被上下文撑宽）
- `{4{4'hFF}}` → 内层 `4'hFF` 先被截成 `4'b1111` → 得 `16'hFFFF`（同时报 `vlog-2600 Redundant digits`）
- 易混：`{4{4'h1}}` = `16'h1111`（不是 ffff）；`{16{1'b1}}` = `16'hFFFF`

**两条硬约束（均实测报错）**：

1. 内层字面量**必须定宽**。`{4{'hFF}}` 里 `'hFF` 是 unsized（按 32 位算）→ 结果 128 位并报
   `vopt-2121 Illegal concatenation of an unsized constant`
2. 重复次数**必须是常量**。`{n{4'hF}}`（n 是变量）→ `vlog-8303 Repetition multiplier must be constant.`
   （要动态重复只能用 for 循环 + 移位/动态数组）

## 五、嵌套花括号不改变宽度

```systemverilog
{{16'hFF},{16'hFF}}   // 实测 $bits = 32
```

- `{{a},{b}}` ≡ `{a,b}`，也与 `{2{16'hFF}}` 同为 **32 位**
- 只有 `{2{8'hFF}}` 才是 16 位
- 赋给 16 位的 `arrt[0]` → 静默截断只留低 16 位（`Warnings: 0`）；用 `{{16'hAA},{16'hBB}}` 验证，存活的是 `00bb`

**正确写法**（要填两个 16 位切片）：

```systemverilog
arrt[1:0] = {{16'hFF},{16'hFF}};   // arrt[1]=00ff, arrt[0]=00ff，无警告
```

> ⚠️ 不要写 `arrt[31:0]`：索引会先按第一维 `[3:0]` 解释，31 出界 → `vopt-2697`。
> 维度范围选择的方向：`arrt[3:2] = {16'hAAAA, 16'hBBBB}` → **首值给大索引**（arrt[3]=aaaa）。

## 六、赋值模式 `'{...}` 的方向

```systemverilog
arry = '{A, B, C};   // 实测：arry[2]=A, arry[1]=B, arry[0]=C
```

**第一个值给最大索引**——和直觉相反，是定长/非打包数组赋值的常见错点（与 C 语言初始化列表方向相反）。

## 七、定长数组没有 `.size()`

```systemverilog
bit v[4];
v.size();      // ❌ vlog-13276 Could not find field/method name (size)
$size(v);      // ✅
```

`.size()` **只属于动态数组 / 队列 / 关联数组**；定长数组用 `$size()`。这不是工具 bug，是 LRM 规定。
