> 功能覆盖率回答一个问题：**"我设计的激励，到底打到了哪些场景？"**
> 本篇既有语法速查，也有一个耗了 10+ 轮才定位的 Questa 大坑。

## 一、covergroup / coverpoint / bins

```systemverilog
covergroup cg @(posedge clk);
  cp_a: coverpoint a;                                  // 自动划分 bin
  cp_b: coverpoint b {
    bins low  = {[0:3]};                               // 命名 bin
    bins high = {[4:7]};
  }
  cx: cross cp_a, cp_b;                                // 交叉覆盖
endgroup
```

| 概念 | 含义 |
| --- | --- |
| covergroup | 一组覆盖点的集合，需 `new()` 后用 `sample()` 采样 |
| coverpoint | 一个变量/表达式的取值分布 |
| bins | 取值被划进的"格子" |
| cross | 两个 coverpoint 的组合（笛卡尔积） |

- 命名 bin：`bins low = {[0:3]}`（区间）或 `bins x = {1, 3, 5}`（枚举集合）
- 不写 bins 时按 `auto_bin_max` **自动划分**
- `covergroup` 是类，可 `new()` + 传参 + `sample()`

## 二、bin 划法决定数字（实测对比）

**同一份激励**，只改 bin 的定义，覆盖率天差地别：

| 项目 | 覆盖率 | bins |
| --- | --- | --- |
| `cp_a`（3 个命名 bin） | **100.00%** | 3/3 |
| `cp_b`（3 个命名 bin） | **100.00%** | 3/3 |
| `a`（8 个自动 bin） | 75.00% | 6/8 |
| `b`（8 个自动 bin） | 62.50% | 5/8 |
| `cx_named`（3×3） | 44.44% | 4/9 |
| `cx_raw`（8×8） | 17.18% | 11/64 |
| **TOTAL** | **66.52%** | 32/95 仓 |

两条结论：

1. **bin 越细，数字越低** → 不同 bin 定义的覆盖率**不可横向比较**
2. **不要为了刷指标把 bin 划粗** —— 那是在掩盖验证缺口

> ⚠️ **别把最后一列当分母**：`32/95` 只是"命中仓数/总仓数"，`TOTAL` 并不这样算（32/95 = 33.68%）。
> 真实口径是**各项等权平均**：`(100+100+75+62.5+44.44+17.19)/6 = 66.52%`。详见第十节。

## 三、auto_bin_max 默认 64

Questa 对 coverpoint 的自动 bin 数量默认上限是 **64**（`auto_bin_max`）。
所以 8 位变量**不会**生成 256 个 bin，最多 64 个。
（上表 `cx_raw` 的 64 = 两维自动 bin 的积。）

## 四、cross 总是最后满

交叉覆盖的空间是各维度 bin 数的**乘积**，需要场景组合。
实测 `cx_raw`（8×8=64）只有 17.18%，是全场最低——**cross 天然最难填满，别指望随机跑满**。

## 五、⚠️ Questa 覆盖率"看起来不工作"的根因

> **Questa 控制台模式下，TB 里的 `$finish` 会终止 `-do` 脚本。**
> 所以写在 `run -all` **之后**的 `coverage save` / `coverage report` 根本执行不到
> —— 命令不报错，但等于没写。

这就是长期"覆盖率出不来"的真凶。历史误判过的假设（config_db、`-cover` 字母含义、
license 过期、PATH 被 modelsim_ase 抢先）**均不成立**：
`which vsim` 确认是 `/e/questasim/win64/vsim`，license 含 `vsimcoverage_c`（有效期至 2036）。

## 六、正确的覆盖率流程

```bash
# ① 编译期插桩（必须）
vlog -work w -sv -cover bsectf xxx.sv

# ② 运行期保留覆盖率（必须）——注意 save 写在 run 之前
vsim -work w -coverage -c top -do "coverage save -onexit c.ucdb; run -all; quit -f"

# ③ 官方报告工具
vcover report -cvg -details c.ucdb
```

**两种等价解法**：

| 解法 | 适用 | 命令 |
| --- | --- | --- |
| A | TB **无** `$finish` | `-do "run 200ns; coverage save c.ucdb; coverage report -cvg -detail; quit -f"` |
| **B（推荐）** | TB **带** `$finish`（唯一可行） | `coverage save -onexit c.ucdb;` **写在 `run` 之前** |

- `vlog` 和 `vsim` **必须同时**带覆盖率选项，缺一不可
- `-onexit` 钩子保证即使之后 `$finish` 也能写盘
- 看报告优先用 `vcover report -cvg -details`，比在 vsim 里 `coverage report` 清爽

**排查顺序（可复用）**：① `vlog -cover` 是否被接受 ② `vsim -coverage` 是否带上
③ **`$finish` 是否吃掉了 `-do` 后续命令**（最高频） ④ `vcover` 直读 ucdb

## 七、从报告读出"验证缺口"

MCDF lab2 实测 `TOTAL COVERGROUP COVERAGE: 53.47%`，6 个 covergroup。
从明细能直接读出 4 个缺口：

| 缺口 | 现象 | 缺什么场景 |
| --- | --- | --- |
| `illegal_access` | 几乎没打 | 缺非法访问 |
| `arbiter_priority` | 仅 25% | 缺 prio 组合 |
| `ch0_en~ch2_en` | 各 50% | 只测"开"，没测"关" |
| `formatter_grant` | 33% | 缺 grant 延迟 |

> 覆盖率的价值不在数字高低，而在**指着明细告诉你"哪块场景还没打"**——这才是收敛的靶子。

## 八、数组仓 `bins x[] = {[8:$]}`：方括号决定"粒度"

```systemverilog
kind: coverpoint tr.kind {          // kind 是 4 bit → $ = 15
  bins zero = {0};                  // 1 个仓
  bins lo   = {[1:3], 5};           // 1 个仓（合并仓：1/2/3/5 挤在同一个桶里）
  bins hi[] = {[8:$]};              // 8 个仓（数组仓：每个取值各自一个）
  bins misc = default;              // 兜底（不计入总数）
}
```

- **`[]` 跟在 bin 名后面 = 数组仓**：区间里**每个取值各自一个仓**；不写 `[]` 则整段区间算 **1 个仓**。
- 仓数 = 区间内取值个数 = `$ - 8 + 1` = **8**（`$` 表示该表达式的最大值 = 15）。
- Questa 实测（采样 0~15，`vcover report -cvg -details`）：

| 写法 | Questa 报出的仓名 | 命中次数 |
| --- | --- | --- |
| `bins zero = {0}` | `zero` | 1 |
| `bins lo = {[1:3], 5}` | `lo` | **4（仍是 1/1 仓）** |
| `bins hi[] = {[8:$]}` | `hi[8] hi[9] … hi[15]` | 各 1 |
| `bins misc = default` | `default bin` | 3（值 4/6/7） |
| `bins whole = {[8:$]}`（无 `[]`） | `whole` | 8 |

**三个必须记住的点**：

1. ★ **仓名用"取值"命名，不是从 0 开始的下标**：`bins b[] = {1,2,3}` → 报出 `b[1] b[2] b[3]`；`bins r[] = {[4:6]}` → `r[4] r[5] r[6]`。**别按"下标从 0 编号"的直觉去引用单个成员。**
2. **`default` 仓不计入 bins 总数、也不参与 cross**（报告里单列，`covered/total bins` 里看不到它）。
3. 合并仓会把漏测**藏起来**：`lo` 命中 4 次仍显示 100%，看不出 1/2/3/5 里哪个没打到；数组仓才能逐个交代。`$` 依赖变量位宽——若变量只有 3 bit（`$=7`），`[8:$]` 就是**空区间**。

## 九、cross 里裁剪分母：`ignore_bins` / `binsof` / `intersect`

```systemverilog
cross kind, port {
  ignore_bins hit = binsof(port) intersect {7};                        // ① 剔掉 port=7 整列
  ignore_bins md  = binsof(port) intersect {0}
                    && binsof(kind) intersect {[9:11]};                // ② 剔掉 3 个格子
  ignore_bins lo  = binsof(kind.lo);                                   // ③ 剔掉 kind.lo 整行
}
```

| 词 | 角色 | 作用 |
| --- | --- | --- |
| `ignore_bins` | cross 里的 bin 声明 | 声明一批**要剔除**的交叉仓：不统计、不计入分母；**命中了也不报错** |
| `illegal_bins` | 同上 | **命中立即报错**（当断言用）；"不该发生"的组合用它 |
| `binsof(cp)` / `binsof(cp.bin)` | 集合函数 | 取该 coverpoint 的**全部仓** / **指定仓**（只能用在 cross 的筛选表达式里） |
| `intersect {值域}` | 求交 | 按**取值**把左边的仓集合过滤一遍 |
| `&&` / `\|\|` / `!` | 条件组合 | 多个筛选条件相与/相或/取反 |

**实测（kind 10 仓 × port 16 仓 = 160）**：三条规则净剔 **28** 个（① 10 + ② 3 + ③ 16 − 重叠 1 个 `<lo,port[7]>`）→ 分母 **132**（`vcover` 实测正是 132）。

**另一种等价写法是"白名单"**：在 cross 里直接写命名 `bins`，**分母就等于这些命名仓的个数**，不是自动笛卡尔积 —— MCDF 的 `cg_mcdf_reg_illegal_access` 就是这么做的（12 个命名仓 → 分母 12）。

**为什么必须裁剪**：非法地址空间 `[8'h20:$]` 有 224 个取值、非法数据 `[8'h40:$]` 有 192 个，若让交叉对每个取值都建仓，**分母会膨胀到几百上千且永远填不满**，覆盖率数字就失去指导意义。裁剪的原则是：**只保留有代表性的组合**。

> ★ **cross 里每条 bins_selection 都必须以 `;` 结尾**（缺分号：`(vlog-13069) near "ignore_bins": syntax error, expecting ';'`）。

## 十、★ 覆盖率分数的口径（最容易算错的地方）

| 层级 | 怎么算 |
| --- | --- |
| 单个 coverpoint / cross | 命中仓 ÷ 该项总仓数（`default` / `illegal_bins` 不计入） |
| 单个 covergroup | 它的各项（coverpoint + cross）百分比的**加权平均**（默认权重 1） |
| `type_option.weight = 0` | **把该项从评分里剔除**（只做统计、不参与打分） |
| `$get_coverage()`（整个仿真） | **所有 covergroup 分数的算术平均**（每个 CG 等权，**与仓数无关**） |

**实测验证（MCDF lab2，Questa 10.7c）**：

- `cg_formatter_length` 没设 weight → `(id 100% + length 75%) ÷ 2 = 87.5%` ✓
- `cg_mcdf_reg_write_read` / `cg_mcdf_reg_illegal_access` / `cg_channel_disable` 把 `addr`/`cmd`/`wdata`/`rdata` 这些"只为喂 cross"的 coverpoint **全设了 `weight = 0`** → 它们的分数**就等于各自主 cross 的分数**：`66.66%(12/18)`、`41.66%(5/12)`、`66.66%(12/18)` ✓
- basic test 总分 `53.47 = (66.67+41.67+66.67+25+87.5+33.33) ÷ 6` ✓
- full_random 总分 `41.89 = (66.67+41.67+55.55+25+29.16+33.33) ÷ 6` ✓

> **两个实用推论**：
> ① 报告里的 `covered/total bins`（本次 32/95 仓）**只是数仓用的，不是总分**；一个 64 仓的 cross 和一个 3 仓的 coverpoint 在总分里**权重相同**。
> ② 想让某个 coverpoint "只统计不拉分"，就给它 `type_option.weight = 0`（MCDF 的常规手法）。

## 十一、随机 vs 定向：为什么"随机测试覆盖率反而更低"（实测）

**同一套 covergroup，只换 test**（MCDF lab2，Questa 10.7c）：

| covergroup | basic（定向） | full_random（随机） |
| --- | --- | --- |
| `cg_mcdf_reg_write_read` | 66.7 | 66.7 |
| `cg_mcdf_reg_illegal_access` | 41.7 | 41.7 |
| `cg_channel_disable` | 66.7 | **55.6** ↓ |
| `cg_arbiter_priority` | 25.0 | 25.0 |
| `cg_formatter_length` | **87.5** | **29.2** ↓↓ |
| `cg_formatter_grant` | 33.3 | 33.3 |
| **`$get_coverage()`** | **53.47** | **41.89** |

**6 个里 4 个完全相同**，只有两个变了 —— 所以"随机更低"不是笼统印象，而是有具体机制：

```systemverilog
// mcdf_full_random_test 的寄存器配置：三个通道的 len/prio/en 都随机抽
wr_val = ($urandom_range(0,3)<<3) + ($urandom_range(0,3)<<1) + $urandom_range(0,1);
//        ↑len∈{4,8,16,32}       ↑prio∈{0..3}          ↑en∈{0,1} ← 关键
```

- 本次抽到"**只有 ch1 使能、len=32**"，且 **bin 计数 `999998` 证明这个配置整条 run 再没变过**（`ch0_dis`/`ch1_en`/`ch2_dis` 从头到尾一个状态）。
- 于是 formatter 只看到 1 种 `chid`（1/3）和 1 种 `length`（1/4）→ `(33.3+25)/2 = 29.2%`；
- `cg_channel_disable` 的 en 维度与 `*_en_vld` 交叉同样被冻结 → `10/18 = 55.6%`。

**三层原因**：

1. **配置类随机是"一锤定音"的**：一个 `$urandom_range` 决定整条 run 的激励空间。定向测试则把三个通道都打开、长度分别取 8/16/32 —— **精确地把关键取值点了一遍**。
2. **随机有负向连锁**：`en=0` 不只少测一个 bin，它**掐掉下游一整片**（formatter 的 chid/length、en×vld 交叉）。
3. **单次随机 run ≠ 随机验证**：呼应 [[SV · 随机约束]] 里 dist 的结论（期望比例 + 统计波动），单次随机覆盖到哪一段是碰运气的；正确用法是 **多 seed × 回归**。

**结论**：定向保证**深度**（关键场景/边界/非法访问精确打到），随机保证**广度**（撒出人想不到的组合），再用覆盖率当路标形成闭环：红 bin → 补 test → 再跑收敛。

> 实操提醒：**别只看 TB 打印的总数**（53.5 vs 41.9），那会把局部缺口平均掉 —— 要**逐 covergroup** 比，才看得出是 formatter 那两个在拖后腿。
