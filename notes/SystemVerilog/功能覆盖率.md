> 功能覆盖率回答一个问题：**"我设计的激励，到底打到了哪些场景？"**
> 本篇既有语法速查，也有一个耗了 10+ 轮才定位的 Questa 大坑。

## 一、covergroup / coverpoint / bins

```systemverilog
covergroup cg @(posedge clk);
  cp_a: coverpoint a;                                  // 自动划分 bin
  cp_b: coverpoint b {
    bins low  = {[0:3]};                               // 命名 bin
    bins high = {[4:7]};
  }
  cx: cross cp_a, cp_b;                                // 交叉覆盖
endgroup
```

| 概念 | 含义 |
| --- | --- |
| covergroup | 一组覆盖点的集合，需 `new()` 后用 `sample()` 采样 |
| coverpoint | 一个变量/表达式的取值分布 |
| bins | 取值被划进的"格子" |
| cross | 两个 coverpoint 的组合（笛卡尔积） |

- 命名 bin：`bins low = {[0:3]}`（区间）或 `bins x = {1, 3, 5}`（枚举集合）
- 不写 bins 时按 `auto_bin_max` **自动划分**
- `covergroup` 是类，可 `new()` + 传参 + `sample()`

## 二、bin 划法决定数字（实测对比）

**同一份激励**，只改 bin 的定义，覆盖率天差地别：

| 项目 | 覆盖率 | bins |
| --- | --- | --- |
| `cp_a`（3 个命名 bin） | **100.00%** | 3/3 |
| `cp_b`（3 个命名 bin） | **100.00%** | 3/3 |
| `a`（8 个自动 bin） | 75.00% | 6/8 |
| `b`（8 个自动 bin） | 62.50% | 5/8 |
| `cx_named`（3×3） | 44.44% | 4/9 |
| `cx_raw`（8×8） | 17.18% | 11/64 |
| **TOTAL** | **66.52%** | 32/95 |

两条结论：

1. **bin 越细，数字越低** → 不同 bin 定义的覆盖率**不可横向比较**
2. **不要为了刷指标把 bin 划粗** —— 那是在掩盖验证缺口

## 三、auto_bin_max 默认 64

Questa 对 coverpoint 的自动 bin 数量默认上限是 **64**（`auto_bin_max`）。
所以 8 位变量**不会**生成 256 个 bin，最多 64 个。
（上表 `cx_raw` 的 64 = 两维自动 bin 的积。）

## 四、cross 总是最后满

交叉覆盖的空间是各维度 bin 数的**乘积**，需要场景组合。
实测 `cx_raw`（8×8=64）只有 17.18%，是全场最低——**cross 天然最难填满，别指望随机跑满**。

## 五、⚠️ Questa 覆盖率"看起来不工作"的根因

> **Questa 控制台模式下，TB 里的 `$finish` 会终止 `-do` 脚本。**
> 所以写在 `run -all` **之后**的 `coverage save` / `coverage report` 根本执行不到
> —— 命令不报错，但等于没写。

这就是长期"覆盖率出不来"的真凶。历史误判过的假设（config_db、`-cover` 字母含义、
license 过期、PATH 被 modelsim_ase 抢先）**均不成立**：
`which vsim` 确认是 `/e/questasim/win64/vsim`，license 含 `vsimcoverage_c`（有效期至 2036）。

## 六、正确的覆盖率流程

```bash
# ① 编译期插桩（必须）
vlog -work w -sv -cover bsectf xxx.sv

# ② 运行期保留覆盖率（必须）——注意 save 写在 run 之前
vsim -work w -coverage -c top -do "coverage save -onexit c.ucdb; run -all; quit -f"

# ③ 官方报告工具
vcover report -cvg -details c.ucdb
```

**两种等价解法**：

| 解法 | 适用 | 命令 |
| --- | --- | --- |
| A | TB **无** `$finish` | `-do "run 200ns; coverage save c.ucdb; coverage report -cvg -detail; quit -f"` |
| **B（推荐）** | TB **带** `$finish`（唯一可行） | `coverage save -onexit c.ucdb;` **写在 `run` 之前** |

- `vlog` 和 `vsim` **必须同时**带覆盖率选项，缺一不可
- `-onexit` 钩子保证即使之后 `$finish` 也能写盘
- 看报告优先用 `vcover report -cvg -details`，比在 vsim 里 `coverage report` 清爽

**排查顺序（可复用）**：① `vlog -cover` 是否被接受 ② `vsim -coverage` 是否带上
③ **`$finish` 是否吃掉了 `-do` 后续命令**（最高频） ④ `vcover` 直读 ucdb

## 七、从报告读出"验证缺口"

MCDF lab2 实测 `TOTAL COVERGROUP COVERAGE: 53.47%`，6 个 covergroup。
从明细能直接读出 4 个缺口：

| 缺口 | 现象 | 缺什么场景 |
| --- | --- | --- |
| `illegal_access` | 几乎没打 | 缺非法访问 |
| `arbiter_priority` | 仅 25% | 缺 prio 组合 |
| `ch0_en~ch2_en` | 各 50% | 只测"开"，没测"关" |
| `formatter_grant` | 33% | 缺 grant 延迟 |

> 覆盖率的价值不在数字高低，而在**指着明细告诉你"哪块场景还没打"**——这才是收敛的靶子。
