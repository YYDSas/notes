> UVM 新手第一关：**"到底什么时候发生了什么？"**
> 结论均来自本机 QuestaSim 10.7c（UVM 1.1d）的实测 + `E:\questasim\verilog_src\uvm-1.1d\src\` 源码。

## 一、九个公共相位 + runtime 子相位

**公共相位（9 个，串行老链）**：

```
build → connect → end_of_elaboration → start_of_simulation → run
      → extract → check → report → final
```

**runtime 子相位（12 个，装在名为 `uvm_sched` 的 schedule 里）**：

```
pre_reset → reset → post_reset → pre_configure → configure → post_configure
→ pre_main → main → post_main → pre_shutdown → shutdown → post_shutdown
```

## 二、两条并行时间线（先记住现象）

| 写法 | 实测日志 |
| --- | --- |
| 只写 `run_phase` | 一条线：@0 start → @4ns end |
| 只写 `main_phase` | 一条线：@0 → @2ns |
| **两个都写** | **两边都在 @0 开工**，日志是两条并行时间线的合并输出 |

> 日常理解用这一句就够：**九相位是串行老链；UVM 在 `run` 的位置并行挂了第二条链
> （reset→configure→main→shutdown）；两条链同时跑，日志只是按时间合并打印。**
> "域（domain）"这个词只在讲 `jump` 时才需要提。

源码根据（`uvm_domain.svh`）：

```systemverilog
m_common_domain.add(domain, .with_phase(m_common_domain.find(uvm_run_phase::get())));
```

→ uvm 域作为 common 域的子节点**挂在 run 相位位置、与 run_phase 并行执行**。

## 三、function phase 不能消耗时间

```systemverilog
function void build_phase(...);
  #2ns;      // ❌ (vlog-13114) Timing control in function is illegal.
endfunction
```

- 只有 **`run_phase` 与 runtime 子相位**（pre_reset/reset/…/post_shutdown）是 `task`，可消耗时间
- 其余八个公共相位（build/connect/end_of_elaboration/start_of_simulation/extract/check/report/final）
  都是 `function`，**零耗时**
- 查法：`uvm_component.svh` 里 `extern virtual function|task void xxx_phase(uvm_phase phase)`
- 所以日志里 @0 会出现一片打印——那是 function phase 在时间 0 内走完

## 四、链内串行，链间并行（实测决定性证据）

实测 `reset_phase` 里加 `#2ns`：

```
@0     run_phase start
@0     reset_phase start
@2000  reset end
@2000  main start        ← 前一个相位占的时间，原样推后了后面的相位
@3000  run end
```

> **链内串行**：前面相位占用的时间，原样推后同链后面**所有**相位，绝不抢先。
> **链间并行**：run 侧与新链同时开工，互不影响。

## 五、各组件 phase 的执行顺序（实测）

| 相位 | 顺序 | 实测 |
| --- | --- | --- |
| `build_phase` | **自顶向下**（父先子后） | `uvm_test_top → c0 → c1 → c2` |
| `connect_phase` | **自底向上**（子先父后） | `c0 → c1 → c2 → uvm_test_top` |
| `end_of_elaboration_phase` | **自底向上** | 同上 |
| `run_phase` | **并发** | 四个组件都在 @0ns 开跑 |

- **同一 phase 内不同组件的调度顺序不确定**（实测 START 打印顺序 test→c2→c1→c0，不是创建顺序）
  → 代码**不能依赖"谁先跑"**

## 六、⚠️ 相位开始后才 create 的组件不会补跑

在 `run_phase` 里 create 的组件，它的 `build_phase` 与 `run_phase` **都不执行**，
而且 **0 错 0 警、完全静默**（实测 `late_create_demo` 只有 test 自己的打印）。

> **组件必须在 `build_phase` 里建好。**

## 七、`super.<phase>()` 加不加？（源码 + 实测）

源码（`uvm_component.svh` 注释原文 "For backward compatibility, they call the old style name"）：

| 相位方法 | 内部会调用 |
| --- | --- |
| `run_phase` | `run()` |
| `build_phase` | `m_build_done=1; build()` |
| `connect_phase` | `connect()` |
| `end_of_elaboration_phase` | `end_of_elaboration()` |
| `start_of_simulation_phase` | `start_of_simulation()` |
| `extract/check/report_phase` | `extract()/check()/report()` |

实测 4 例：

- 父类实现 `run_phase`：子类**不调** super → 只打印 CHILD；**调** super → 打印 BASE + CHILD
- 父类只写旧式 `run()`：不调 super 时旧式 `run()` **不出现**；调 super 才出现
  → 证明 **super 的职责就是调旧式名**

> **最需要记住的一条**：
> ```systemverilog
> // uvm_sequencer_base::run_phase 的实现
> super.run_phase(phase);
> start_default_sequence();
> ```
> 自定义 sequencer 覆盖 `run_phase` 时**忘了 super，`default_sequence` 就不会启动**。

## 八、objection 机制

- `uvm_phase` 内部有成员 `phase_done : uvm_objection`（`uvm_phase.svh:509`）
  —— **每个 phase 各自的计分板**；`raise_objection/drop_objection` 只是它的包装
- `get_objection_total(obj=null)` 文档原话：
  **"Returns the current number of objections raised by the given object and all descendants."**
  → 是**当前净计数**（raise +1 / drop −1），且含所有子孙组件

实测（`objection_probe.sv`）：

```
@3000  total = 3 BEFORE clear
[OBJTN_CLEAR] Object 'common.run' cleared objection counts for run
       total = 0 AFTER clear        ← 之后再 drop 自己仍是 0，不会变负
```

- 语义探针：某组件 1ns 时 drop 自己，3ns 读 `TOTAL = 2`（不是 3）→ 证实是**净计数**；
  `get_objection_count()` 可按 objector 查单计数
- ⚠️ `phase.clear()`（= `phase_done.clear(this)`）会**掐断**组件里没跑完的代码
- 备选：书 p.220 的 `force_drop_objections()` 用 `get_objectors()` 名单逐个正规 drop
  （**走机制、不掐断**），更推荐

## 九、`phase.jump()`

```systemverilog
extern function void jump(uvm_phase phase);   // 源码 uvm_phase.svh:440
```

| 要点 | 说明 |
| --- | --- |
| 是 **function（非阻塞）** | 调用即返回，实际切换发生在当前相位结束（objection 掉光）时 |
| 参数是**目标相位的对象句柄** | `uvm_reset_phase::get()` 取单例，**不是字符串名** |
| **域级**操作 | `uvm_domain::jump()` 注释："jumps all active phases of this domain"，遍历本域所有活跃相位 |
| 只作用于自己域 | 所以激励要放在 reset/main 子相位，而不是 `run_phase` |
| `uvm_phase::jump_all()` | 可让所有 schedule 一起跳 |

**实测等价 demo**：

```
@0ns   reset_phase（清队列/数组）
@1ns   main_phase (pass 1)
@3ns   jump back to pre_reset_phase
[PH_JUMP] phase main (domain uvm) is jumping to phase pre_reset
@3ns   reset_phase 重跑 → @4ns main_phase (pass 2)，0 error 0 fatal
```

**为什么连 test 也跟着跳**：相位对象（`uvm_main_phase::get()`）是**全局单例**，
不属于任何单个组件；jump 遍历本域所有活跃相位。
实测跳转后第二轮 reset 有 3 条 `phase running` = comp[0] + comp[1] + **test**。

**推论**：

1. 统一复位本就是设计意图
2. "只让 comp[0] 调 jump" 只是避免重复发起，**不代表只有它跳**
3. 想让组件不参与跳转，只能 `set_domain()` 放到另一个域；**只写 `run_phase` 的组件会掉队**

**书写要点**：`reset_phase` 必须能干净重来（清队列/状态）；跳转前处理好 objection；
只跳一次（用计数控制）。生产环境应由专门的 reset 监听组件统一发起。

## 十、怎么判断某相位属于哪个域

公开 API：`uvm_phase::get_schedule_name()`、`get_domain_name()`、`get_domain()`
（UVM 的 `[PH_JUMP]` 消息内部就用它们）。

实测：

| 相位 | domain | schedule |
| --- | --- | --- |
| build / connect / start_of_simulation / run / report | `common` | 空 |
| reset / configure / main | `uvm` | `uvm_sched` |

**规律**：公共 9 相位直接挂在 common 域下（无 schedule 节点）；runtime 子相位装在
`uvm_sched` 里再挂进 uvm 域（所以日志是 "schedule uvm_sched, domain uvm"）。
