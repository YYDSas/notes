> 组件（层次 + 生命周期）与对象（无层次 + 值语义）是两条不同的继承链。
> 工厂（factory）则决定了"写的是基类名，造出来的是什么子类"。

## 一、uvm_object vs uvm_component

| | `uvm_object` | `uvm_component` |
| --- | --- | --- |
| 继承自 | `uvm_void` | `uvm_report_object` |
| 有层次吗 | ❌ 无 | ✅ 有 name / parent |
| 构造 | `new(string name="")` | `new(string name, uvm_component parent)` |
| 生命周期 | 用完即弃 | 随仿真一直存活 |
| 典型 | sequence / sequence_item / config | driver / monitor / agent / env / test |

**关键洞察**：`uvm_port_base`（各类 port / export / imp）**继承自 `uvm_component`**，
所以它的构造函数是 `new(name, parent)`——**port 是有层次的组件，不是普通对象**。

```systemverilog
uvm_blocking_put_port #(mon_data_t) mon_bp_port;
// new 里： mon_bp_port = new("mon_bp_port", this);   ← this 是 parent
```

## 二、组件树与层次名

```systemverilog
class my_env extends uvm_component;
  my_agent agt;
  function void build_phase(uvm_phase phase);
    agt = my_agent::type_id::create("agt", this);   // ← parent = this，挂进树
  endfunction
endclass
```

- `build_phase` **自顶向下**：父组件先建，才能给孩子当 parent
- 层次路径由 name 逐级拼成：`uvm_test_top.env.agt.drv`
- 顶层 test 固定叫 **`uvm_test_top`**

**config_db 传 vif 的标准套路**：

```systemverilog
// tb 顶层
uvm_config_db#(virtual chnl_intf)::set(null, "uvm_test_top.env.agt.*", "vif", intf);
// 组件里
if (!uvm_config_db#(virtual chnl_intf)::get(this, "", "vif", vif)) `uvm_fatal(...)
```

## 三、get_name / get_type_name / get_full_name

| 方法 | 返回 | 实测（base_c 被 override 成 x_c） |
| --- | --- | --- |
| `get_name()` | new() 时传入的**实例名** | `c1` / `c2`（各不同） |
| `get_type_name()` | **override 后的实际类名** | `x_c` / `x_c` |
| `get_full_name()` | 层次路径 | `uvm_test_top.c1` |
| `get_object_type()` | 工厂代理 wrapper | `c1.get_object_type().get_type_name()` = `x_c` |
| `T::type_name` | **静态变量**（不带括号） | `base_c` |

源码（`macros/uvm_object_defines.svh`）：

```systemverilog
`define m_uvm_get_type_name_func(T) \
   const static string type_name = `"T`"; \
   virtual function string get_type_name (); \
     return type_name; \
   endfunction
```

- `get_type_name()` 是 `` `uvm_*_utils `` 宏生成的**虚函数**
- **`uvm_object::get_type_name()` 基类实现返回 `"<unknown>"`**
  → **忘写 utils 宏就是这个症状**，是极好的排错线索

> `get_type_name()` 是验证「工厂 override 是否生效」**最快**的手段。

## 四、工厂 create 与 override

```systemverilog
class base_c extends uvm_component;
  `uvm_component_utils(base_c)
  function new(string name, uvm_component parent); super.new(name, parent); endfunction
endclass

class x_c extends base_c;
  `uvm_component_utils(x_c)
endclass

// 想用 x_c 顶替 base_c：
base_c::type_id::set_type_override(x_c::get_type());   // 或在 build_phase 里
base_c b = base_c::type_id::create("b", this);         // 实际造出 x_c
```

- **必须有 `` `uvm_component_utils `` 注册**，工厂才认识这个类
- 推荐写法：统一用 `type_id::create(...)`，不要直接 `new()`
  （直接 `new()` 会绕过工厂，override 失效）

## 五、override 生效时机（实测 6 条）

教材在 `build_phase` 里"先 create 再 override"，注释写着 `// too late`。实测补充：

| 步骤 | 行为 |
| --- | --- |
| 1. `set_type_override_by_type(A, X)` → `create` | 造出 `X`（**创建前 override 生效**） |
| 2. 再 `set_type_override_by_type(A, Y)` | 已创建实例**仍是 X**（对已创建无效） |
| 3. 但这一步没白费 | 工厂表被替换为 A→Y，之后新建的 comp2 = **Y**（日志 `[TPREGR] ... Replacing with override ...`） |
| 4. **正确位置** | 在创建任何组件之前设 override。test 的 `build_phase` 先于 env 的（自顶向下），放在 **test.build_phase 开头** ✓ |
| 5. 命令行 `+uvm_set_type_override=A,B` | 在 build_phase 之前生效（日志 `[UVM_CMDLINE_PROC]`），**优先级最低**，会被代码里的 override 替换掉 |
| 6. 消息 id 版本差异 | UVM 1.2 用 `[TPRGRS]`（分两行），UVM 1.1d 用 `[TPREGR]`（合并一行），语义相同，别误判 |

> 一句话：**override 是"查表时刻"的规则**——create 时查一次表。
> 想让 override 生效，必须在 create 之前设置。

## 六、为什么工厂值得学

- **不改源码换实现**：同一套 TB，用 mock / 不同版本组件替换某实例
- **test 不改 env**：只换 sequence / 换 driver 的子类
- 同类思路的另一层：**Verilog `config` 的库绑定**（编译/链接期换整个模块，同名模块分放不同库）
  → 见 [[仿真工具 · Verilog config 与库绑定]]
