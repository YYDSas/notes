> "这条警告太吵了""这个 error 能不能降级成 info" —— 报告机制就是干这个的。
> 它的一个反直觉点：**severity override 不递归、也不被子组件继承**（实测 5 组对照）。

## 一、四个维度

```systemverilog
`uvm_info("ID", "message", UVM_MEDIUM)
`uvm_warning("ID", "message")
`uvm_error("ID", "message")
`uvm_fatal("ID", "message")
```

| 维度 | 取值 |
| --- | --- |
| **severity** | `UVM_INFO / UVM_WARNING / UVM_ERROR / UVM_FATAL`（另有 `UVM_NONE`） |
| **id** | 自定义字符串，用来分组/过滤 |
| **verbosity** | `UVM_NONE(0) < UVM_LOW(100) < UVM_MEDIUM(200) < UVM_HIGH(300) < UVM_FULL(400) < UVM_DEBUG(500)` |
| **action** | 报告后干什么（打印/计数/退出） |

- 只有 `verbosity ≤ 当前阈值` 的消息才会打印（`+UVM_VERBOSITY=UVM_HIGH` 命令行可调）
- `UVM_FATAL` 默认 action 是 **退出仿真**

## 二、severity override 严格是"单组件"的（实测）

```systemverilog
set_report_severity_id_override(UVM_WARNING, "RUN", UVM_INFO);
// 把「severity=WARNING 且 id="RUN"」降级为 INFO
```

实测（组件树 `uvm_test_top → c1 → c2`，c1 里还有一个 c2）：

| 实验 | test 自己 | 3 个子组件的 6 条警告 |
| --- | --- | --- |
| 只对 test 设 override | 降级为 INFO ✓ | **仍全部是 WARNING** |
| **创建子组件之前**对 test 设 override | 降级为 INFO ✓ | **仍全部是 WARNING**（不继承！） |
| 教材递归版（depth=10） | ✓ | 6 条全部降级为 INFO |
| 改进版（公开 API 递归） | ✓ | 6 条全部降级为 INFO |
| `set_report_severity_id_action_hier(UVM_WARNING,"RUN",UVM_NO_ACTION)` | ✓ | 6 条全部被屏蔽 |

> **结论**：severity override **不递归，也不被子组件继承**（与创建先后无关）。
> 想影响整棵树，必须自己递归遍历，或用自带的 `_hier` 版本。

## 三、`_hier` 家族：**唯独没有 `override_hier`**

源码 `uvm_component.svh:1276-1362`，三类都有递归版本：

| 类别 | 递归版本 |
| --- | --- |
| verbosity | `set_report_verbosity_level_hier` |
| action | `set_report_severity_id_action_hier` |
| file | `set_report_severity_id_file_hier` |
| **severity override** | ❌ **没有** `set_report_severity_id_override_hier` |

UVM 自己的 `_hier` 实现（`uvm_component.svh:2182`）就是
"先作用于自己 + `foreach(m_children[c])` 递归"，与教材手写版同构。

**实用替代**：只想**消音**不要降级时，直接用自带的
```systemverilog
set_report_severity_id_action_hier(UVM_WARNING, "RUN", UVM_NO_ACTION);
```
不必手写递归。

## 四、API 分三层

| 层次 | 调用 |
| --- | --- |
| 组件级 | `comp.set_report_severity_id_override(cur, id, new)` |
| 处理器级 | `comp.get_report_handler().set_severity_id_override(cur, id, new)` |
| 自带递归 | `set_report_severity_id_action_hier(...)` 等 |

**建议调用位置**：`end_of_elaboration_phase`（组件树已建完）。

## 五、访问权限暗礁（写递归时要小心）

| 成员 | 权限 | 源码 |
| --- | --- | --- |
| `m_rh`（report handler） | **public** | `uvm_report_object.svh:83` |
| `m_children` | **protected** | `uvm_component.svh:1612` |

- `children[i].m_rh` 合法（public）
- 直接 `h.m_children[i]` 是**踩边界写法**：Questa 10.7c 接受了，**VCS/Xcelium 可能拒绝**
- 稳妥写法：`c.get_report_handler()` + `h.get_children(kids)`（都是公开 API，实测效果一致）

## 六、消息 ID 用哪个名字？

| 写法 | 显示 | 语义 |
| --- | --- | --- |
| `` `uvm_info(get_type_name(), msg, UVM_LOW) `` | `[name_test]` | **按类分组**（UVM 惯例） |
| `` `uvm_info(get_name(), msg, UVM_LOW) `` | `[uvm_test_top]` | 按实例分组 |

（实测 report summary 里两个 ID 各计 1 次。）

> 大平台里消息成千上万，**用 `get_type_name()` 当 ID 才能按"类"聚合统计**——
> 这也是 UVM 官方示例统一这么写的原因。

## 七、⚠️ 写这类代码必踩的编译坑

```systemverilog
function void my_func();
  m_rh.set_severity_id_override(...);   // 语句
  uvm_component children[$];            // ❌ Illegal declaration after the statement
endfunction
```

**SystemVerilog 规定块内声明必须在任何语句之前**（每个嵌套块各自遵守；VCS/Questa/Xcelium 一致）。
修正：把声明提到函数开头；`if` 块内的声明也要放块首。

> 这条正是 [[错题本 · 代码书写类]] 里的高频错误，写报告递归时几乎必踩一次。
