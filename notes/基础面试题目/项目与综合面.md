# 面试题 · 项目与综合面

> 汇总自《面试总结》项目问题（第 1~21 题）、验证部分第 8/19/20/33~37 题。
>
> ⚠️ **这类题没有标准答案**。这里的模板是原文里的**答题框架**，`□` 是**你要替换成自己项目内容**的地方。
> 原则：**说清"设计文档说什么 → 你提取了什么功能点 → 怎么写用例 → 遇到什么问题 → 怎么解决 → 最终覆盖率多少"**。

## 一、项目类问题的通用答法

面试官问"你的验证环境怎么搭的"，本质是在问四件事：

1. **你懂不懂这个 IP 的功能**（有没有真的读过规格）
2. **功能点怎么变成测试点**（有没有方法论）
3. **遇到问题能不能 debug**（有没有真干过）
4. **结果如何**（覆盖率、发现了什么 bug）

只答第 4 层的（"我搭了个 UVM 环境跑通了"）是拿不到分的。

## 二、验证环境

### 1. 验证环境如何搭建的？

答题骨架：

```plain
项目背景：□（什么协议/什么模块/什么位宽）
读文档：□（从规格书提取了哪些功能点）
环境架构：□（几个 agent、几个 sequencer、scoreboard 怎么比）
用了什么 UVM 特性：□（config_db 传什么、factory 有没有用、RAL 有没有用）
遇到的问题和解决：□
最终结果：代码覆盖率 □%，功能覆盖率 □%，发现了 □ 个 bug
```

### 2. transaction / item 包含哪些？

按"**协议上有的字段**"逐个说，并说明**哪些是 rand、哪些是约束来的**：

```plain
□ 的 transaction 包含：
  - rand 字段（激励空间）：□
  - 非 rand 字段（响应/状态）：□
  - 约束：如保留位约束为 0、addr 范围约束 inside {…}
```

> 加一句"传输时间戳用 `uvm_field_int(..., UVM_ALL_ON | UVM_DEC)` 注册进 field_automation，scoreboard 靠它比对期望值和实际值的时间对齐"→ 立刻拉开和背模板的人差距。

### 3. 功能点如何提取？

见 [[面试题 · 验证方法与流程]] 第 8 题（测试点分解）。项目里要说清：

- 依据哪份文档（功能规格 / 架构规格）
- 用了哪几种分解方法（等价类、边界值、正交、错误推断）
- 举例说明某个具体的测试点是怎么推出来的

### 4. 某项目中有哪些测试点？

按九类框架列（时钟/复位/接口时序/数据通路/异常处理/典型电路/DFX/性能/压力），然后**挑 2~3 个最具体的展开**：

```plain
□ 项目的一个具体测试点：
  功能点：□
  推导过程：比如"配置寄存器 A 的范围是 [3,8]，所以用边界值分析法得到
            1,2,3,4,7,8,9,10 这几个配置值都要测"
  激励怎么发：□（随机 + 约束，还是定向）
  怎么判断通过：scoreboard 比什么 / 断言检查什么 / 覆盖率看哪个 bin
```

### 5. DUT 的功能是什么？

一分钟讲清：这块电路干什么用、有哪几个主要模块、对外接口是什么、关键寄存器有哪些。

```plain
□ DUT 主要做 □，包含 □ 个模块：
  - □（模块 A 功能）
  - □（模块 B 功能）
  对外接口：□（信号名、位宽、时钟频率）
  关键寄存器：□（地址、名称、读写属性、复位值）
```

### 6. Virtual sequence 里有哪些东西？

- 各个底层 sequence 的成员（句柄）
- 配置对象（active/passive、vif、参数）
- `body()` 里的**跨接口协调逻辑**：谁先启动、谁等谁、条件依赖

```systemverilog
class test_seq extends uvm_sequence #(item, rsp);
  `uvm_object_utils(test_seq)

  apb_write_seq      apb_w;
  apb_read_seq       apb_r;
  uvm_event          ev_done;      // 跨接口同步

  virtual task body();
    fork
      apb_w.start(p_sequencer.apb_sqr);
      apb_r.start(p_sequencer.apb_sqr);
    join
  endtask
endclass
```

> 强调一句"**virtual sequence 本身不发 transaction，只做调度和跨接口同步**"，这是与 hierarchical sequence 的分界线。

### 7. 如何配寄存器？寄存器如何和 driver 做互动？

**配寄存器**：`uvm_config_db#(uvm_object_wrapper)::set(this, "env.agent", "default_sequence", reg_hw_reset_seq::type_id::get())`，或用 `set_config_int` 把 `vif` 传下去。

**和 driver 互动**：寄存器模型产生 `uvm_reg_bus_op` → `adapter::reg2bus()` 转成 bus 事务 → `bus_driver` 按**总线时序协议**驱动。driver 里用 `get_next_item` 拿到事务，按 APB/AHB 的时序逐拍驱动。

### 8. Scoreboard 怎么写的？怎么比较数据的？

```plain
1) 数据从哪来：
   - monitor → analysis_port → scb 的 analysis_imp
   - reference model 自己产生期望值
2) 比什么：
   - 逐字段比（address / data / len）
   - 或用 field_automation 的 compare
3) 怎么处理顺序：
   - 队列 / fifo 按时间戳对齐
   - 或用 uvm_event / mailbox 同步
4) 不一致时：
   - $error 打印不一致的字段和 transaction 快照
   - 从波形定位到对应时间段
```

### 9. 断言检查了哪些时序？

按模块列具体的：

```plain
- 请求/应答握手：valid 保持到 ready
- 数据稳定：valid && ready 时 addr/data 保持不变
- 复位释放后 N 拍内不允许发起请求
- 计数器溢出保护
- 状态机非法跳转 assert property
```

> 有真实例子最好："用 `assert property (@(posedge clk) disable iff (rst) req |-> ##[1:3] ack)` 抓过一次 ack 超时的问题"。

### 10. 仿真环境的打印是如何实现的？

```systemverilog
`uvm_info("SEQ/START", $sformatf("start %s, addr=0x%0h", get_name(), addr), UVM_LOW)
```

分级：`uvm_info` / `uvm_warning` / `uvm_error` / `uvm_fatal`，配 `set_report_verbosity_level` 或命令行 `+UVM_VERBOSITY=UVM_HIGH` 控制冗余度。

### 14. 代码和功能覆盖率为什么没到 100%？

- **代码**：可能 RTL 某些条件分支没跑到
- **功能**：一些关心的值没采样到，可能是因为随机次数少了

### 15. 验证环境中哪些地方会用到约束？

主要是 **item**：数据保留位约束为 0、注入错误激励时约束 `error` 为 1、寄存器保留域约束为 0，等等。

### 16. 寄存器复位和读写怎么测的？

见 [[面试题 · 寄存器模型 RAL]] 第 11 题。

### 17. 写一个寄存器读一个寄存器好，还是全部写完再读好？

**全部写完再读好。** 前门访问每笔消耗仿真时间，批量后减少事务切换、回归更快，也让 scoreboard 的比对窗口更清晰。

### 18. RAL 里 set 了之后总线上一直 get 不到 transaction，怎么解决？

**大概率是 adapter 在 `reg2bus()` 转换过程中出错。** 排查：`reg2bus` 有没有被调到、生成的地址/操作类型对不对、`default_map` 的 `set_sequencer()` 有没有设、map 基地址 + reg 偏移算出来对不对。

### 19. 两个设计人员设计了两个功能相同的 DUT，你如何判断哪个更好？

**考虑面积与功耗**（综合后对比）。补充维度：时序余量、面积、可综合性、可读性、可维护性。

### 20. 验证结构（这个怎么答？）

画出来最直观：

```plain
uvm_test_top
└── env
    ├── bus_agent (ACTIVE, SPI)
    │   └── driver / sequencer / monitor
    ├── reg_agent  (ACTIVE, 自定义寄存器接口)
    │   └── driver / sequencer / monitor
    ├── irq_agent  (PASSIVE, 只收中断)
    │   └── monitor
    ├── reference_model
    ├── scoreboard
    └── coverage
```

说清每个 agent 是 ACTIVE 还是 PASSIVE、为什么这么分（引出"为什么需要 is_active"）。

### 21. DUT 的 bug 有哪些？

举例要挑**能体现分析过程**的，不要只说"发现一个 bug"：

```plain
例 1：UART —— 设计里没有给寄存器做复位操作。
      通过"复位之后的读写测试"发现：复位之后读出来的值不对，补不出 0。
      定位过程：前门写→前门读比对 → 发现读值是旧值
                → 用后门 peek 确认模型侧值正确
                → 排除验证环境问题 → 交给设计
```

> 注意第一个例子的教训：**"先写再读"这种测试发现不了地址映射错误**，必须前门 + 后门结合（见 [[面试题 · 寄存器模型 RAL]] 第 9 题）。

## 三、综合面（软性问题）

### 1. 为什么选择验证岗位？为什么转行？

四条，按"行业→兴趣→性格→待遇"排：

1. **行业前景**：芯片国产替代是大势所趋，IC 发展前景更广阔，更利于今后的发展。
2. **喜欢工作内容**：验证需要理解待测设计、提取功能点、搭建验证环境、大规模随机测试、debug、回归迭代、收集覆盖率，整个过程连下来很有成就感，尤其享受遇到问题、解决问题的过程，**尤其环境跑通的时候**。
3. **性格适合**：不喜欢太多社交，喜欢一门心思搞技术、喜欢钻研。验证工作量大、繁琐，要求细心且耐心，不急躁，思考问题全面。
4. **待遇**：IC 的薪资待遇高于行业平均水平（出身农村家庭，做验证能更好缓解家庭压力），也能为公司创造更大价值。

> ⚠️ 第 4 条建议**慎说或不说**，很多面试官会觉得"你只是为钱"。可以改成"希望在有技术含量的方向上长期深耕"。

### 2. 验证人员应具备哪些品质？

1. 对任何东西都要**有质疑的态度，精益求精**——如对覆盖率要力求尽量达到最高。
2. 不但精通验证，**对于设计以及后端也要熟悉**。
3. 对自己不懂的问题要**虚心求教，不能模棱两可**。

### 3. 验证中遇到过哪些问题？怎么解决的？

准备**三个层次**的例子（由浅入深）：

```plain
1) 平台搭建：最大的困难就是搭建一个能跑通的验证平台。看懂和自己动手写是两码事，
   会遇到很多错误，通过看 log 不断 debug。
   例：项目里 agent 很多，如何例化、连接；scb 需要很多端口，还要避免方法名重复
       → 用 uvm_analysis_imp_decl 加后缀 / 改用 tlm_analysis_fifo 解决
2) 时序理解：时序一旦理解出错，driver 驱动和 monitor 收集都会出错，scb 比对也会错。
   例：某模块中没有时序，不知道 monitor 该怎么收集数据
       → 最后用 uvm_event 做同步
3) 覆盖率：如何针对未覆盖的地方写新 case 需要自己慢慢分析。
   例：实习时参考模型是同事用 matlab 写的
       → matlab 如何与验证环境适配成了问题
       → 最后把 matlab 处理后的数据输出到一个文档里，scb 再从文档读数据
```

### 4. 相对于科班的优势？

1. **更强的自学能力和更坚定的决心**，能够不断学习和探索新知识技能。转 IC 那段时间经常学到半夜一两点。
2. **更广泛的知识背景和多元化的学习经历**，能更快适应工作环境、应对挑战，综合素质更强。

### 5. 遇到的最大的困难？怎么解决？

讲一个真实的、体现**抗压 + 方法论**的故事。注意要有：背景 → 困难 → 挣扎 → 解决 → 结果。

原文例：本来有希望保研，十月得知不能保研，心情非常低谷，下定决心考研，最后三个月挑灯夜战、每天学习 12 小时、卸载所有社交娱乐软件，成功上岸。秋招期间看到别人拿 offer 也会焦虑，就去黄浦江边散步平复情绪，回来继续学习——**机会只会留给有准备的人**。

### 6. 职业规划？

```plain
未来 5 年内：脚踏实地不断积累技术，丰富验证经验，在团队里保持谦虚的态度和前辈学习，打好基础。
5-10 年内：成为团队的核心成员，在大型项目里担任重要职责；
           同时学习了解芯片的其他流程（芯片设计和芯片后端），
           成为发展全面的芯片行业从业者。
```

### 7. 自我评价 / 为什么我们要录用你？

```plain
□ 项目的复杂度（多 agent、AXI、RAL、多时钟域…）
□ 我负责的模块和测试点数量
□ 我发现的 bug 类型（协议违例、边界、时序…）
□ 我用到的技术深度（约束建模、覆盖率建模、debug 手段）
□ 我能带来的价值（能独立搭环境、能 review 设计）
```

## 四、容易被问到的"两个 DUT 比较"和"数据流"

**数据流**：画出 transaction 的完整流向

```plain
sequence.body()
  → start_item / randomize / finish_item
  → sequencer 仲裁
  → driver: get_next_item(req)
  → drive_req(req) → 驱动 virtual interface → DUT
  → DUT 输出
  → monitor 采样 → transaction
  → analysis_port → {reference_model（+ predictor）, scoreboard}
  → scoreboard 比对 → $error / $info
  → coverage.sample()
  → 打印 → log
```

- [ ] 项目类问题**必须带具体数字**（覆盖率 %、agent 数、发现几个 bug）
