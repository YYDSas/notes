# 面试题 · 验证方法与流程

> 汇总自《面试总结》验证部分第 2~10、24~37 题。这部分**最能看出项目经验**，答的时候一定要带自己项目的例子。

## 1. 对 UVM 验证方法学和 UVM 库的理解？

三条：

1. **UVM 以 SV 语言为基础搭建验证平台框架**，把验证过程中可复用和标准化的部分规定在类库里，减轻构建环境的负担——类似 Python 的类库。UVM 的类库主要由 object、component、factory、transaction 和 sequence、report、register model 等组成。
2. **UVM 是一个框架，可以按需要自己搭建**，流程规范。写的时候不用过多考虑语言实现问题，可以把精力放在场景的设计实现上。
3. **UVM 是分层的测试平台**。看起来复杂，但 UVM 把大任务分解成小任务交给各个组件完成，各组件**相互独立又存在联系**，能快速搭建需要测试平台，重用性高，在大型验证中减轻工作负担。

## 2. IC 设计的流程及使用工具？

### 前端设计主要流程

| 阶段 | 内容 | 工具 |
| --- | --- | --- |
| **（1）规格指定** | 客户（Fabless，无晶圆设计公司）提出的功能与性能要求 | — |
| **（2）系统级设计** | 用 matlab / c 等建模，验证方案可行性 | MATLAB / C |
| **（3）RTL 设计** | 用 VHDL / Verilog HDL 把模块功能以代码实现 | — |
| **（4）仿真验证** | 检验编码设计正确性，看是否精确满足规格中所有要求。**设计与验证反复迭代**直到完全符合 | Mentor Modelsim、Synopsys VCS |
| **（5）逻辑综合** | 把 HDL 代码翻译成**门级网表 netlist**。需设定约束条件（面积、时序目标），基于特定综合库 | Synopsys Design Compiler |
| **（6）STA 静态时序分析** | 检查**建立时间 / 保持时间**违例 | Synopsys PrimeTime |
| **（7）形式验证** | 从**功能上**验证综合后的网表。常用**等价性检查**，以功能验证后的 HDL 为参考对比网表功能 | Synopsys Formality |

> **前仿** = RTL 级仿真（Modelsim / VCS），与版图实现无关，**没有时序延时信息**。
> **后仿** = 门级仿真，布局布线之后，考虑真实信号延迟、负载、电源电压变化，验证是否仍满足要求，**会产生 SDF 文件**。
> **（6）（7）属于后仿。**

综合要点：需要基于特定的综合库，不同库中标准单元的面积和时序参数不同 → **选用综合库不一样，综合出来的电路在时序、面积上是有差异的**。

### 后端设计流程

| 阶段 | 内容 | 工具 |
| --- | --- | --- |
| **（1）DFT** | Design For Test，可测性设计。常见方法是在设计中插入**扫描链**，把非扫描单元变为扫描链单元 | Synopsys DFT Compiler |
| **（2）布局规划** | 放置宏单元模块，确定 IP、RAM、I/O 引脚等位置，**直接影响芯片最终面积** | Synopsys Astro |
| **（3）CTS 时钟树综合** | 时钟的布线。使时钟从同一源到各寄存器时**延迟差异最小** | Synopsys Physical Compiler |
| **（4）布线（P&R）** | 标准单元之间的连线。所谓 0.13um / 90nm 工艺，微观上是**金属布线可达的最小宽度**，即 MOS 管的沟道宽度 | Synopsys Astro |
| **（5）寄生参数提取** | 导线电阻、互感、耦合电容会产生噪声、串扰、反射，导致信号完整性问题 | Synopsys Star-RCXT |
| **（6）版图物理验证** | **LVS**（版图 vs 门级电路图）、**DRC**（设计规则检查：间距、线宽）、**ERC**（电气规则：短路开路） | Synopsys Hercules |
| **（7）流片 Tape out** | 所有检查无误后把版图交给 Foundry 做晶圆，再封装测试 | — |

## 3. 形式验证是哪两种？

1. **等价性验证**：从**功能**上对综合后的网表进行验证——以功能验证后的 HDL 为参考，对比网表功能，检验是否等价，保证综合没有改变原 HDL 描述的功能。
2. **模型检查**：从**数学上**完善地检查电路的实现方案是否确实实现了设计描述的功能，建立数学模型检查。

> 与 STA 区分：STA 是**时序上**检查，形式验证是**功能上**检查。

## 4. 什么是覆盖率驱动验证（CDV）？

以**覆盖率的高低作为衡量验证完备性的指标**。验证计划中指定具体覆盖率目标，通过覆盖率验证可以确定验证是否达到要求。

**但**：达到目标覆盖率**并不意味着验证就通过了**。因为功能覆盖率是**人为定义**的，即便达到 100% 也未必覆盖了所有功能场景——人为主观定义时可能有遗漏，所以还需要对测试用例**持续迭代**。

## 5. 验证的完备性怎么理解？

首先，验证**不能保证百分百完备**，但应该朝这个方向努力。通过**多种验证方法**尽可能减少潜在风险——包括 IP 级验证、子系统级验证、SoC 级验证，此外还有 **UPF 验证、FPGA 原型验证**等。

从前端 RTL 验证角度看，完备性主要包括四个方面：

1. 设计 spec 的功能是否**验证到**
2. 所编写的 **testcase 是否全部 pass**
3. **覆盖率**是否达到要求
4. **接口完备性**确认——保证所有接口时序都已覆盖，包括**正常时序及异常时序**

芯片后端也会做一些检查：时序检查、DFT、形式验证。

## 6. SoC 验证与 IP 验证 / 系统级验证与模块级验证的区别？

- **模块级（IP 级）**：更关注模块**内部**的功能——寄存器、数据通路、数据结构、协议信号等细节，**工作量较大**。
- **系统级（SoC 级）**：检查模块**顶层接口**、模块与模块之间的**信号连接**，以及模块组合后的**整体功能**。

## 7. 拿到一个项目（DUT）后，如何开展验证活动？

1. **查看 DUT 设计文档**，弄清 DUT 的功能与接口时序，**提取功能点**
2. **画出验证框图**，展开底层组件
3. **根据细化的功能点编写测试用例**：先写**一个** testcase 和一些基础 sequence，**确保环境能跑通**，再根据其他测试点写新用例
4. **大规模随机测试**，收集代码和功能覆盖率
5. **查看覆盖率报告**，分析哪些还没覆盖，针对未覆盖的地方写**定向测试**以及**更换不同种子**继续跑
6. **回归测试**：把之前的用例再同时跑一遍，在极端情况下找出设计或验证环境的 bug
7. **撰写验证报告**，开会讨论、review

> **回答时必须结合自己项目**：具体项目的功能点有哪些、你是如何针对功能点写 testcase 的、最终代码覆盖率和功能覆盖率是否都到 100%、覆盖率收集语句写在 testbench 的哪些组件中。

## 8. 测试点分解的原则和方法？

### 三条原则

测试点实际是把设计的功能**按层级分解成一个个最简单、最底层的功能点**，化繁为简，方便测试用例的实现。测试点主要从**功能规格与架构规格**中提取。

- **完备性**：不能遗漏任何功能点，**特别是异常处理、边界处理、容错处理**——这些往往最容易被忽视
- **低耦合**：不同测试点之间的相关性甚低最好。这直接决定了**分解粒度**，并影响 testcase 开发难度
- **无歧义**：描述**直接而明确**，不同测试点之间不存在矛盾
- **扩展性**：包含异常和边界特性

### 提取角度（九类）

```text
a. 时钟功能        b. 复位功能        c. 接口时序
d. 数据通路        e. 异常处理        f. 典型电路测试点
g. DFX 测试点      h. 性能测试点      i. 压力测试点
```

### 四种功能测试点分解方法

**A、等价类划分法**：把所有可能的输入数据（有效的、无效的）划分成若干等价类。
例：参数 A 范围 [100,1000] → 可划分为 [100,200]、[200,300]…[900,1000]。

**B、边界值分析法**：对输入的边界条件分析，得出边界值测试点（含正常和异常）。
例：配置寄存器 A 的正常范围是 [3,8]，边界值法可得 **1,2,3,4,7,8,9,10**。

**C、正交矩阵法**：对输入的各个条件正交，筛选出可靠的测试点。
例：参数 A 有开/关两种，参数 B 有模式 1/2 两种，参数 C 位宽有 1bit/8bit/64bit → 正交分解有 **2 × 2 × 3 = 12** 种组合。

**D、错误推断法**：依靠经验、直觉做出判断甚至猜测，给出可能存在缺陷的条件、场景，生成对应的测试点。
例：猜测设计人员可能没考虑**反压**情况 → 增加接口上的反压测试，可通过 force 一定时间的 full / afull 信号观察逻辑处理情况。

**后期**要加入适当的**随机测试点**，覆盖范围会比较广泛、不符合测试点的定义，但没关系——后续随机测试是为了把多种情况混合起来测试，也是一种测试点场景。

### 测试点与测试用例的关系

- 测试用例是**根据测试点写的**，用来覆盖测试点。
- **一个测试用例可以覆盖多个测试点**；在考虑用例复杂度和时间的前提下，单个用例应覆盖尽量多的测试点。
- **单个测试点在一个用例中必须被测试覆盖**，不可出现"多个测试用例都通过后某个测试点才被覆盖"的情况。如果有，必定是**测试点分解太粗**，需要重新细化。

**总结**：一个测试用例可以包含多个测试点；一个测试点不能被分解到被多个测试用例包含（但一个测试点**可以**在多个用例中被包含）。

## 9. 测试用例怎么写？

主要是**写 sequence**，在 `body()` 里根据测试点要求写相应的激励，通过 **scoreboard** 判断 DUT 功能是否正确实现。

## 10. 编写 testcase 的基本思路和顺序？

面试必问。三步：

1. **基本测试用例**：用来把 `tb.sv` 启动、创建 TLM 拓扑结构等，确保 `tb.env` 没有问题。
2. **直接测试用例**：验证 RESET、RAL、FSM、数据读写、算法、固定值测试等。
3. **随机测试用例**：考虑可以随机的测试。

## 11. 仿真过程中遇到问题如何定位？scoreboard 数据出错怎么办？

**scb 中数据比对错误的地方肯定会打印出来**。比如项目里比对的 `ch` 和 `data`，把不一致的 `ch`、`data` 打印出来，然后**从波形中找出对应的 ch 和 data**，检查硬件是不是应该这样处理。

- 硬件处理错误 → 交给设计人员处理
- 验证环境自身问题 → 改验证环境

## 12. 对定向测试和随机测试的认识？

**定向测试**可以找出设计中**预期的漏洞**；**随机测试**覆盖范围往往比定向测试大，能找出**预期之外**的漏洞。

随机测试覆盖不到的地方，需要编写定向测试。当使用随机激励时，需要用**功能覆盖率来评估验证的进展情况**。

## 13. 为什么采用随机化的验证策略？

- 使用随机化产生激励，可以在**很短时间内产生大量随机激励**。
- 对于较大的验证空间，这些随机激励可以达到工程师**可能会忽略的地方**。
- 相对于固定的激励（难以覆盖较大空间），随机化激励**简化代码编写**，更能验证出 DUT 可能隐藏的错误，提高验证完备性。

## 14. 回归测试的作用？

把所有测试用例**不断重复地跑**，进一步发现 DUT 中**隐藏的错误**，提高覆盖率。

## 15. debug 的手段有哪些？

**打印显示、设置断点、波形分析。**

## 16. 覆盖率怎么收敛？（代码 95%、功能 80%、pass 100%）

针对 **RTL 代码没运行的部分**以及**功能覆盖率未采样到的部分**编写新的测试用例，可以**新增约束**或者使用**定向测试**使覆盖率收敛。

## 17. 如果仿真卡住，但时间一直在往前推进，可能是什么原因？

**只考虑验证环境自身的错误**，两种可能：

1. **事件触发晚了**：等待的 `@` 一直没等到，进程一直阻塞，代码无法执行。
2. **用了阻塞函数**：`get()` 从一个**空的 mailbox** 拿 data，或 `put()` 往**满的 mailbox** 放数据。

## 18. 随机种子的理解？

产生随机数的过程中，**如果不改变随机数种子**，每次程序从头开始运行都会产生**相同的随机数序列**。

对 IC 验证来说，如果不改变 seed 值，每次 run 仿真时**仍会产生相同的激励数据**。解决：编译时加

```verilog
+ntb_random_seed_automatic
```

## 19. 仿真效率比较低，通过哪些编码方式可以提高？

1. **循环条件不要带计算**，否则每次循环都要算一次
2. **能条件成立后才进行的计算，就不要放到前面**——条件不成立时那个计算根本执行不到
3. **连接处 `logic` 显式声明成 `wire`**，可以加快仿真速度
4. **尽量用 `ref`**，少传递复杂数据结构
5. **不要滥用动态数据结构**

## 20. 前仿和后仿的区别？前仿能检查亚稳态吗？

**前仿真（RTL 级仿真）**：通过 Modelsim / VCS 验证电路逻辑功能是否正确，即 HDL 描述是否符合设计定义的功能模型。通常与具体电路版图实现无关，**没有时序延时等信息**。

**后仿真（门级仿真）**：基于**布局布线之后**的模型仿真，可以考虑真实的信号延迟、负载、电源电压变化等。目的是在考虑实际因素后验证设计是否仍满足要求，**特别是时序要求**。后仿会产生 **SDF 文件**。

**前仿不能检查亚稳态**——因为前仿没有时序延时信息，亚稳态本质是时序问题。

## 21. 验证无法检查 DUT 的哪些问题？

1. **数据处理效率问题**检测不出来。比如 DUT 中可以插入多个 FIFO 提高效率：一个 buffer 处理完一个数据才能接下一个，两个 buffer 时第二个数据可以放在第二个 buffer 里，第一个处理完立刻切换，节省时间——这种**性能差异 RTL 功能仿真看不出来**。
2. **建立保持时间、亚稳态、竞争冒险**都检查不到。

## 22. 灰盒、黑盒、白盒验证的区别？

- **黑盒**：内部结构**完全不可见**，只能看到设计的输入接口和输出接口。只能**通过设计文档**了解功能。
- **白盒**：内部内容结构**完全可见**，能清楚看到设计细节。好处是能了解**设计者的意图**，验证可以达到设计上的这一点，但需要花更长的时间。
- **灰盒**：内部结构**只有一部分可见**。

## 23. 验证工程师和设计工程师是什么关系？还和谁协作？

**与设计工程师**：设计工程师基于 Verilog 编写 RTL 代码实现设计文档的功能点，然后把代码交付给验证工程师；验证工程师基于 C/C++/SV 搭建验证环境来检测 RTL 是否正确实现了功能点要求，再把发现的 bug 反馈给设计工程师。

**其他协作方**：

| 对象 | 协作内容 |
| --- | --- |
| **架构工程师** | 了解芯片的整体架构和功能点 |
| **DFT 工程师** | 他们也要做测试验证，很多时候他们的验证平台就是从验证工程师的平台**移植**过去的 |
| **FPGA 工程师** | 会复用很多 IC 验证的测试用例，**复现错误现场** |
| **后端工程师** | 如果负责后仿，经常交流，因为后仿的**网表是他们提供的** |
| （只做 IP level 时） | 基本只要和前端设计工程师打交道 |

## 24. 前端 RTL 验证之外，芯片后端还会做哪些检查？

时序检查（STA）、DFT、形式验证。

## 25. VCS 的一个编译过程怎么解释？

```tcl
com:
    vcs -full64 -sverilog +v2k -debug_all -timescale=1ns/1ns -ntb_opts uvm-1.1 \
        -l comp.log \
        -f ./filelist.f \
        -p ${NOVAS_HOME}/share/PLI/VCS/LINUX64/novas.tab ${NOVAS_HOME}/share/PLI/VCS/LINUX64/pli.a \
        tb.sv
```

| 选项 | 含义 |
| --- | --- |
| `-full64` | 以 64 位模式编译 |
| `-sverilog` | 支持 SV 语法 |
| `+v2k` | 支持 Verilog 2001 语法 |
| `-debug_all` | 使能所有 debug 调试功能 |
| `-timescale=1ns/1ns` | 仿真时间单位和精度 |
| `-ntb_opts uvm-1.1` | 加载 UVM 库文件 |
| `-l comp.log` | 仿真信息输出到 log 文件 |
| `-f ./filelist.f` | 指定包含所有文件路径的 filelist |
| `-p` | 指定加载的源文件和动态库 |
| `tb.sv` | 项目顶层文件 |

## 26. 覆盖率怎么收集？用什么仿真软件、哪个指令、文件格式是什么？多个覆盖率文件怎么合并？

| 项 | 答案 |
| --- | --- |
| 软件 | **VCS** |
| 指令 | `-cm`（coverage mode），运行时加 `-cm line+cond+fsm+tgl+branch+assert` |
| 文件格式 | 后缀 **`.vdb`** |
| 合并多个 | `urg_merge`（原 merge） |

## 27. 如何在前期保证提取的功能点完备？

要**充分理解设计文档**，然后根据设计文档提取功能点，遵循测试点分解的**常规方法**细化出测试点——包括正常的、**边界的**以及**异常**的地方。后续再根据**仿真结果**以及**覆盖率报告**进行完善。

## 避坑指南

- [ ] **等式要写全**：一个用例可覆盖多个点；一个点不能拆到多个用例
- [ ] 测试点分解四条原则：完备性（含异常/边界/容错）、低耦合、无歧义、扩展性
- [ ] 覆盖率 100% **不等于**验证通过——功能覆盖率是人为定义的
- [ ] 前仿查不出亚稳态/竞争冒险/保持时间；性能效率也查不出
- [ ] 卡死的两种环境原因：事件等不到、阻塞的 `get`/`put` 卡在空/满 mailbox 上
- [ ] 答"验证完备性"别说"能 100% 覆盖"，要说**不能保证但通过多种方法降低风险**
