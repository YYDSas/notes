# 面试题 · 覆盖率与断言

> 汇总自《面试总结》SV 部分第 10、18~21、33 题。

## 1. 代码覆盖率、功能覆盖率、断言覆盖率分别是什么？

**代码覆盖率**：针对 **RTL 设计代码运行完备度**的体现。工具（VCS / VCG）自动插桩收集。包含：

- **行覆盖率**：各行代码被执行的情况
- **条件覆盖率**：各个条件中的逻辑操作数被覆盖的情况
- **跳转覆盖率（toggle）**：单 bit 信号 0→1 / 1→0 的跳转情况
- **分支覆盖率**：`if / case / for / forever / while` 各分支的执行情况
- **状态机覆盖率**：各种状态被进入的次数以及状态之间的跳转情况

**功能覆盖率**：衡量设计实现的**各种功能是否符合设计文档的功能点要求**。由验证工程师自己建模（covergroup）。

**断言覆盖率**：检查几个信号之间的关系，常用于检查**时序上的错误**，测量断言被触发的频繁程度。

## 2. 代码覆盖率和功能覆盖率"一高一低"分别是什么原因？

### 代码覆盖率低 + 功能覆盖率高

- A、**covergroup 写得不完备**，测试点分解也可能不完备
- B、DUT 中有大量**冗余代码**

### 代码覆盖率高 + 功能覆盖率低

- A、功能覆盖率的**采样有问题**——相关场景都打到了，但 covergroup 没采样到
- B、covergroup 中的一些 **cross bin 或 corner 点没覆盖到**

## 3. 提高覆盖率的方法？

1. **新增约束**
2. **添加测试用例**
3. **使用不同的种子**运行现有测试用例

覆盖率的收集是**迭代过程**，需要不断反复地运行测试用例。

## 4. `covergroup`、`coverpoint`、`bins` 的区别？`sample()` 以哪个对象采样？

**covergroup（覆盖组）**：一种用户自定义的结构类型，一旦定义就可以像 class 一样通过 `new()` 创建多个实例。可以定义在 `module`、`program`、`interface` 以及 `class` 中。

每个覆盖组必须明确：

- 一个时钟事件（同步对覆盖点的采样）
- 一组覆盖点（coverpoints）
- 覆盖点之间的交叉覆盖
- 可选的形式参数
- 覆盖率选项

**coverpoint（覆盖点）**：一个覆盖组可包含多个覆盖点。每个覆盖点有一组**显式 bins 值**，bins 值可由用户自定义，每个 bins 与被采样的变量或其转换有关。一个覆盖点可以是整型变量，也可以是整型表达式。

三类特殊 bin：

| 类型 | 作用 |
| --- | --- |
| `ignore_bins` | 忽略采样到的 bin，**不计入统计** |
| `illegal_bins` | 采样到就报 **error** |
| `binssof ... intersect` | 与给定表达式的交集，常用于 cross |

**`sample()` 以哪个对象采样**：以 **covergroup 关联的采样变量所在的模块/类实例** 为准，用 `sample()` 显式触发采样，或用 `@` 触发。

```systemverilog
covergroup cov_grp;
  cov_p1: coverpoint a;     // cov_p1 是覆盖点名，a 是被采样变量
endgroup

cov_grp cov_inst = new();
cov_inst.sample();          // 收集覆盖率
```

VCG 自带收集**代码覆盖率**的工具；**功能覆盖率**的收集是通过 `sample()` 采样实现的。

## 5. 什么是代码覆盖率收敛？该怎么推进？

**收敛**：通过查看覆盖率报告，分析哪些还没覆盖，针对未覆盖的地方**编写定向测试**以及**更换不同种子**继续跑。

给定"代码覆盖率 95%、功能覆盖率 80%、test pass 100%"，下一步：

- 针对 **RTL 代码没运行的部分**以及**功能覆盖率未采样到的部分**编写新的测试用例；
- 可以**新增约束**或者使用**定向测试**使覆盖率收敛。

## 6. 条件覆盖率没到 100% 说明什么？怎么解决？

**条件覆盖率**衡量每个**子表达式**的结果是否取到 true 或 false。

没到 100% → 判断语句中某个子表达式的结果取值没取到。

**解决**：**查看覆盖率报告**定位到 RTL 代码中的具体位置，看清条件表达式，通过**新增约束**或**定向测试**让子表达式都能取到两种值。

> 这个方法同样适用于"怎么提高代码覆盖率"——**看到什么就覆盖什么**。

## 7. 断言用来做什么？

**断言用来将设计的功能和时序中"应该成立的属性"描述出来。**

可以用来完成：

- 检查设计的内容
- 提高设计的**可视度和调试能力**
- 检查设计特性在验证中**是否被覆盖**

## 8. 立即断言和并行断言的区别？

| | 立即断言（immediate） | 并行断言（concurrent） |
| --- | --- | --- |
| 时序性 | **非时序** | **时序** |
| 关键字 | `assert` | `property` 用来区分 |
| 执行方式 | 执行时如同过程语句，可在过程块或函数/方法中调用 | 与设计模块**一同并行执行** |
| 触发 | 执行到即检查 | **只在时钟边沿激活**，变量值是**采样到的值** |
| 严重级别 | 可结合 `$fatal` / `$error` / `$warning` / `$info` | — |

## 9. 断言的编写分哪三层？

1. **激励序列 sequence 的编写**：把多个信号的关系用断言中特定的操作符表示。
2. **属性 property 的编写**：可以把多个 sequence 和多个 property 进行嵌套，外加触发事件。
3. **assert 的编写**：调用 property 即可。

写完断言后可以用在很多地方，比如 interface 处——基本能检测信号的地方都可以放断言。

## 10. DPI 是什么？SV 和 C 之间怎么对应？

**DPI（Direct Programming Interface）** 能连接 SV 与其他编程语言（如 C/C++）。通过 `import` 导入一个 C 子程序，就可以像调用 SV 子程序一样调用它。

- 最基本传递类型是 `int`（**双状态 32 位**）。
- 通过 `import` 声明定义 C 任务/函数的原型。
- **有返回值的 C 函数** → 映射成 SV `function`；**void 的 C 函数** → 映射成 SV `task` 或 `void` 函数。
- 通过 `"DPI-C"` 引入的 C 函数可以直接在 `function` 中调用，**但只在该 DPI 被声明的范围内有效**。

### 类型映射表

| SV | C |
| --- | --- |
| `byte` | `char` |
| `int` | `int` |
| `bit` | `svBit` |
| `logic`, `reg` | `svLogic` |
| `shortint` | `short int` |
| `longint` | `long long int` |

**工程做法**：在 package 中封装所有 DPI 函数，打包为 function，然后在需要的地方 `import` 这个 package。使用 `DPI-C` 关键字，用**压缩值（packed）**方式保存数据类型。

> 实测细节见 [[仿真工具 · Questa 避坑手册]] 的 DPI 一节：C 侧回调 SV **task** 时 import 必须写 `context task`。
